# v0.2.0 Release and Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 发布包含当前 `main` 功能的 `v0.2.0`，并将正式实例升级到该镜像。

**Architecture:** 使用现有 tag-triggered GitHub Actions 发布流程构建并推送多架构镜像与 Release 附件。应用配置仍由 homelab-ops 的 Files on Server compose 管理，发布后只将镜像标签更新为不可变的 `0.2.0`，在 .24 拉取并重建容器，最后通过健康检查和系统信息接口验证。

**Tech Stack:** Git、Go、Vue/Vite、Docker Buildx、GitHub Actions、Docker Compose、SSH。

**Spec:** 用户确认版本 `v0.2.0`，并在本次会话临时授权执行发布与 .24 部署；不得修改长期仓库安全约束或读取密钥。

## Global Constraints

- `v0.1.0` 已存在；本次只能创建 `v0.2.0`，不得移动或覆盖旧 tag。
- 发布提交遵循 `🔖 release: v0.2.0`，不添加任何署名 trailer。
- 发布前必须通过 `scripts/check.sh`。
- compose 使用 `ghcr.io/lonelyman0108/ferry:0.2.0`，不得改为 `latest`。
- Ferry 数据目录 `/opt/docker/service/ferry/data` 不得删除、覆盖或迁移。
- 不读取 `.env`、token、Vaultwarden 或其他凭据文件。
- 远程操作只允许 Ferry 目标目录、容器和健康检查；不得修改其他服务。

## Review Focus

- 旧 tag：`v0.1.0` 必须保持指向原提交；在 tag 前检查远端是否已存在 `v0.2.0`。
- 发布工作流失败：发布后先确认镜像 manifest 和版本接口，再执行部署。
- 数据持久性：升级前后确认 compose 仍挂载 `./data:/data`，且升级命令不含 down、volumes 或删除数据。
- GitOps 漂移：部署仓库 compose 与 .24 实际 compose 必须都指向 `0.2.0`。
- 回滚：若健康检查失败，只将 compose 镜像恢复为 `0.1.0` 并重新 `pull/up`，不删除数据目录。
